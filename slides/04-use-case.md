## Workflow 4 ขั้นที่ใช้จริง

```
1) เรียก skill grill-me / grilling   →  Claude ซักถามความต้องการทีละข้อ
2) เข้า plan mode                    →  Claude ร่างแผนเป็นไฟล์ให้ตรวจ
3) ExitPlanMode (อนุมัติแผน)         →  Claude ลงมือสร้างไฟล์ทั้งชุด
4) ทบทวน/แก้ไขเป็นรอบ ๆ              →  ปรับ scope, เพิ่มเนื้อหา
```

4 ขั้นนี้คือกระดูกสันหลังของหัวข้อทั้งหมดวันนี้ — จำให้ได้ ใช้ซ้ำได้กับทุกงาน

<!-- เขียน workflow นี้ไว้บนกระดานหรือปักหมุดสไลด์นี้ค้างไว้ระหว่างสาธิต จะได้ชี้กลับมาได้ตลอด -->

## ขั้น 1 — grill-me: ซักถามทีละข้อ

แทนที่จะรีบเขียนโค้ดจากโจทย์ที่ยังคลุมเครือ ให้เรียก skill ก่อน:

```
/grill-me
# หรือ skill "grilling" ของ mattpocock
```

Claude จะเดินไล่ **decision tree ทีละกิ่ง** พร้อมเสนอคำตอบแนะนำในแต่ละข้อ
ผู้เรียนตอบไปเรื่อย ๆ จนสเปกชัดขึ้นทีละคำถาม

> บทเรียน: **การถูกซักช่วยจับข้อขัดแย้งได้เร็ว** — ก่อนจะเสียเวลาสร้างของผิด

<!-- ขั้นนี้สำคัญที่สุดในการปลูกฝัง mindset "อย่ารีบเขียนโค้ด" ย้ำว่านี่คือสิ่งที่แยก Claude Code ออกจากการ copy-paste prompt ทั่วไป -->

---

## ของจริง: โจทย์ตั้งต้นคลุมเครือ

โจทย์ตั้งต้น (สรุปจาก session จริงที่สร้าง workshop นี้):

> *"สร้างโปรเจกต์เตรียมการสอน Claude Code 1 วัน (10:00–12:00, 13:30–16:30)
> lab ต้องมี install บน Windows + WSL + ใช้ SSH จาก Windows ไป WSL แล้วสั่ง
> Claude Code ทำงานที่นั่น โดยเครื่องไม่มี admin ของ Windows"*

โจทย์แบบนี้มีจุดต้องตัดสินใจซ่อนอยู่เยอะ: มี admin จริงไหม? auth ยังไง?
เน็ตเปิดไหม? → จึงเริ่มด้วยการ **ให้ Claude ซักก่อน** แทนรีบลงมือ

<!-- นี่คือโจทย์จริงที่ใช้สร้าง workshop เดียวกันนี้เอง ให้ผู้เรียนเห็นว่าเป็น meta-example -->

## ของจริง: ตัวอย่างคำถาม grill-me (1/2)

| คำถาม | คำตอบที่เลือก | ผลต่อ design |
|---|---|---|
| เครื่องมี admin/WSL ติดตั้งไว้ไหม? | เครื่องเปล่า ไม่มี admin | ติดตั้ง WSL สดไม่ได้ → WSL เป็น self-study |
| Linux ปลายทางมาจากไหน? | เตรียมทั้ง WSL (เผื่อ) + Linux server ภายนอก | ออกแบบ 2 tracks |
| auth Claude Code ยังไง? | Console API key (เมนู login ข้อ 2) | ตั้ง spend limit รวม, key ต่อคน |

<!-- ชี้ให้เห็นว่าแต่ละคำตอบ "ผลต่อ design" จริง ๆ ไม่ใช่แค่ข้อมูลลอย ๆ — นี่คือจุดที่ grilling สร้างมูลค่า -->

## ของจริง: ตัวอย่างคำถาม grill-me (2/2)

| คำถาม | คำตอบที่เลือก | ผลต่อ design |
|---|---|---|
| เน็ตเวิร์ก? | เปิด ต่อนอกได้อิสระ | ไม่ต้อง config proxy |
| topology ของ VM? | 1 VM/คน มี root | สะอาดสำหรับ install DB/Grafana |
| Claude Code รันที่ไหน? | native บน Windows, สั่งข้าม SSH ไป VM | สถาปัตยกรรมหลัก |
| โฟกัส workshop? | Skills + use case นี้เป็นหลัก, Ivanti เป็น optional | ปรับลำดับเนื้อหา |

<!-- 7 คำถามรวมทั้ง 2 สไลด์นี้คือของจริงทั้งหมดจาก log การสร้าง workshop — ไม่ได้แต่งเพิ่ม -->

## ของจริง: ข้อขัดแย้งที่จับได้ตั้งแต่คำถามแรก

> **"ไม่มี admin" ขัดกับ "ให้ติดตั้ง WSL"**

โจทย์ตั้งต้นขอให้ lab มี "install บน Windows + WSL" แต่พอถูกซักคำถามแรก
(เครื่องมี admin ไหม?) คำตอบคือ **ไม่มี admin** — ซึ่งทำให้ **ติดตั้ง WSL สด
ในห้องเรียนไม่ได้เลย**

**ผลลัพธ์การแก้ปัญหา:** ปรับ WSL ให้เป็น **self-study** (ไม่ทำสดในห้อง)
แทน แล้วเตรียม Linux server ภายนอกเป็นอีก track

> บทเรียน: การถูกซักช่วยจับข้อขัดแย้งได้เร็ว **ก่อน** จะเสียเวลาสร้างของผิด

<!--
นี่คือตัวอย่างที่ทรงพลังที่สุดของหัวข้อนี้ — เล่าให้ผู้เรียนเห็นภาพว่า
ถ้าไม่ได้ถูกซัก คนสร้างอาจจะเขียน lab ที่สั่ง "install WSL" ไปแล้ว
แต่พอเจอเครื่องจริงในห้องเรียนที่ไม่มี admin จะรันไม่ได้ทันที.
การซักถามช่วยเจอ blocker นี้ตั้งแต่ต้น ไม่ใช่ตอนสอนจริง.
-->

## ขั้น 2 — plan mode: ร่างแผนก่อนสร้าง

หลังสเปกชัดจากการซัก Claude เข้า **plan mode**:

- เขียนแผนลงไฟล์ `.md` (โครงไฟล์, agenda, รายละเอียดแต่ละ artifact, วิธี verify)
- **ยังไม่แตะไฟล์จริงของโปรเจกต์** — เป็นแค่แผนให้ตรวจ
- ผู้ใช้อ่านแผน แก้ scope/รายละเอียดได้ก่อนอนุมัติ

จุดสำคัญ: การเห็นภาพรวมทั้งหมดก่อนลงมือ ช่วยจับปัญหาได้ถูกที่ ถูกเวลา
(ก่อนโค้ดถูกเขียน ไม่ใช่หลังรื้อทิ้ง)

<!-- ย้ำว่า plan mode คุ้มค่าที่สุดกับงาน "ใหญ่" หรือ "มีหลายไฟล์" ไม่จำเป็นสำหรับงานเล็กมาก ๆ -->

---

## ขั้น 3 — ExitPlanMode: อนุมัติแผน

`ExitPlanMode` คือจุดที่ผู้ใช้ **อนุมัติ** ให้ Claude ลงมือจริง

พออนุมัติแล้ว Claude จะ:
- สร้างโครงโฟลเดอร์ (`mkdir -p ...`)
- เขียนไฟล์ทีละไฟล์ (README, agenda, `lab/*`, `scripts/*`, `slides/*` ...)
- รันคำสั่งที่จำเป็น (พร้อม permission prompt ให้ผู้ใช้เห็นและอนุมัติทีละครั้ง)

ระหว่างสาธิต ให้ชี้ให้ผู้เรียนเห็น: permission prompt คืออะไร, การรันคำสั่ง,
การแก้ไฟล์ — นี่คือช่วงที่ "เห็นของจริงทำงาน"

<!-- ย้ำเรื่อง permission prompt เป็นกลไกความปลอดภัย ไม่ใช่ความน่ารำคาญ — ให้ผู้เรียนอ่าน diff ก่อนกด allow เสมอ -->

## ขั้น 4 — วนทบทวน/แก้ไขเป็นรอบ ๆ

งานจริงไม่เคยเสร็จในรอบเดียว — feedback ที่เกิดขึ้นจริงระหว่างสร้าง workshop นี้:

```

```

> บทเรียน: **ให้ feedback เป็นรอบ ๆ** — เปลี่ยน scope กลางทางได้ Claude ปรับตาม

## ขั้นตอนแนะนำสำหรับ mini-project


## ทริคที่ควรเน้นกับผู้เรียน

- **ให้ context ดี ๆ**: บอกเป้าหมาย ข้อจำกัด ตัวอย่าง input/output
- **ใช้ plan mode ก่อนงานใหญ่**: ตรวจแผนถูก ประหยัดเวลา/โทเคน
- **`CLAUDE.md`**: บันทึกกติกา/บริบทที่อยากให้ Claude จำทุกครั้ง
- **อ่าน diff ก่อนกด allow**: เข้าใจว่าจะแก้อะไร

## สิ่งที่ผู้เรียนควรถอดบทเรียน (จาก session จริง)

1. **อย่ารีบเขียนโค้ด** — ให้ Claude ซักจนสเปกชัด (skill grilling ช่วยได้)
2. **ใช้ plan mode กับงานใหญ่** — เห็นภาพรวม ตรวจก่อน ลดการรื้อ
3. **ให้ feedback เป็นรอบ ๆ** — เปลี่ยน scope กลางทางได้ Claude ปรับตาม
4. **บันทึก context ใน `CLAUDE.md`** — ให้ Claude จำกติกาโปรเจกต์
5. **ทุกอย่างนี้ทำซ้ำได้เอง** — ดู `lab/04-use-case-build-workshop.md`

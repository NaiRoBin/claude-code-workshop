# Best practices ที่ควรจำ

<!--
เข้าสู่ส่วนสำคัญที่สุดของสไลด์นี้ — best practices 6 ข้อ
แต่ละข้อจะแตกเป็นสไลด์ของตัวเองในหน้าถัดไปเพื่อขยายรายละเอียด
-->

---

## Best practices ที่ควรจำ — ภาพรวม

1. ให้ context ดี
2. ใช้ plan mode กับงานใหญ่
3. `CLAUDE.md`
4. อ่าน diff ก่อน allow
5. ทำงานเป็นรอบเล็ก ๆ
6. ใช้ skill ซ้ำงานประจำ

<!--
ภาพรวม 6 ข้อก่อนลงรายละเอียดทีละข้อ ให้ผู้เรียนเห็นโครงทั้งหมดก่อน
-->

---

## 1. ให้ context ดี

**ให้ context ดี** — เป้าหมาย, ข้อจำกัด, ตัวอย่าง input/output

- เป้าหมาย (goal) ของงานที่ต้องการให้ทำ
- ข้อจำกัด (constraints) ที่ต้องเคารพ
- ตัวอย่าง input/output ให้ Claude เห็นภาพชัด

<!--
ยิ่ง context ชัดเท่าไหร่ Claude ก็ยิ่งตอบสนองตรงความต้องการมากขึ้น
สามอย่างที่ควรให้เสมอ: เป้าหมายคืออะไร, มีข้อจำกัดอะไรบ้าง,
และมีตัวอย่าง input/output ให้ดูไหม
-->

---

## 2. ใช้ plan mode กับงานใหญ่

**ใช้ plan mode กับงานใหญ่** — ตรวจแผนก่อน ลดการรื้อ ประหยัดเวลา/โทเคน

- ตรวจแผนก่อนลงมือทำจริง
- ลดการรื้องานที่ทำไปแล้ว (rework)
- ประหยัดเวลาและโทเคนในระยะยาว

<!--
งานใหญ่ ๆ ควรให้ Claude วางแผนก่อน (plan mode) แล้วเราตรวจแผนก่อนอนุมัติ
ช่วยลดโอกาสที่ต้องรื้อทำใหม่ และประหยัดทั้งเวลาคนและโทเคนที่ใช้
-->

---

## 3. `CLAUDE.md`

**`CLAUDE.md`** — บันทึกกติกา/บริบทให้ Claude จำทุกครั้ง

```
CLAUDE.md
```

- ใช้เก็บกติกาและบริบทของโปรเจกต์
- Claude จะอ่าน/จำสิ่งที่บันทึกไว้ทุกครั้งที่ทำงาน

<!--
CLAUDE.md คือไฟล์ที่ใช้บันทึกกติกา บริบท หรือข้อตกลงของโปรเจกต์
เพื่อให้ Claude Code อ่านและจดจำได้ทุกครั้งที่เริ่มงานใหม่ ไม่ต้องอธิบายซ้ำ
-->

---

## 4. อ่าน diff ก่อน allow

**อ่าน diff ก่อน allow** — เข้าใจการเปลี่ยนแปลงเสมอ (เราคุมได้)

- ตรวจ diff ทุกครั้งก่อนอนุมัติให้ Claude ดำเนินการ
- เข้าใจการเปลี่ยนแปลงเสมอ — เราเป็นคนคุมสถานะสุดท้าย

<!--
ก่อนกด allow ทุกครั้ง ควรอ่าน diff เพื่อเข้าใจว่า Claude กำลังจะเปลี่ยนแปลงอะไร
คนยังเป็นผู้คุมสุดท้ายเสมอ — Claude เป็นผู้ช่วย ไม่ใช่ผู้ตัดสินใจแทน
-->

---

## 5. ทำงานเป็นรอบเล็ก ๆ

**ทำงานเป็นรอบเล็ก ๆ** — commit บ่อย, ทบทวนบ่อย

- แบ่งงานเป็นรอบย่อย ๆ
- `commit` บ่อย ๆ เพื่อเก็บ checkpoint
- ทบทวนผลงานบ่อย ๆ ระหว่างทาง

<!--
แทนที่จะให้ Claude ทำงานก้อนใหญ่ทีเดียว ควรแบ่งเป็นรอบเล็ก ๆ
commit บ่อยเพื่อมี checkpoint ให้ย้อนกลับได้ และทบทวนผลงานบ่อย ๆ
เพื่อจับปัญหาได้เร็วก่อนที่จะสะสมมาก
-->

---

## 6. ใช้ skill ซ้ำงานประจำ

**ใช้ skill ซ้ำงานประจำ** — แพ็ก workflow ที่ทำบ่อยเป็น skill

- งานที่ทำซ้ำ ๆ บ่อย ๆ ควรแพ็กเป็น skill
- ใช้ซ้ำได้เร็วกว่าเขียน prompt ใหม่ทุกครั้ง

<!--
ถ้ามี workflow ที่ทำซ้ำบ่อย ๆ ในงานประจำ ควรแพ็กเป็น skill ไว้ใช้ซ้ำ
ต่อยอดจาก Lab ก่อนหน้าที่สอนสร้าง skill เอง
-->

---

# ความปลอดภัย & ค่าใช้จ่าย

<!--
เปลี่ยนหัวข้อไปเรื่องความปลอดภัยและค่าใช้จ่าย ซึ่งเป็นเรื่องที่ต้องระมัดระวัง
เมื่อใช้ Claude Code ในงานจริง โดยเฉพาะงานที่แตะระบบ/เงิน
-->

---

## ความปลอดภัย

> อย่า commit secret (API key, token) — ใช้ environment variable

- **อย่า commit secret** (API key, token) ลงใน repo
- ใช้ **environment variable** แทนการฝัง secret ในโค้ด
- อ่าน diff/permission ก่อนให้รันคำสั่งที่กระทบระบบ (โดยเฉพาะบน VM ที่มี root)

<!--
ข้อควรระวังด้านความปลอดภัย 2 เรื่องหลัก:
1) ห้าม commit secret เช่น API key หรือ token ลง repo เด็ดขาด — ให้ใช้ environment variable แทน
2) ต้องอ่าน diff และ permission ก่อนอนุมัติคำสั่งที่กระทบระบบเสมอ
   โดยเฉพาะเมื่อทำงานบน VM ที่มีสิทธิ์ root เพราะผลกระทบจะรุนแรงกว่า
-->

---

## ค่าใช้จ่าย

> API key มี spend limit — ระวังงานที่วน/รันยาว

- API key มี **spend limit** (วงเงินการใช้จ่าย)
- ต้องระวังงานที่ **วนซ้ำ (loop)** หรือ **รันยาว** เพราะอาจใช้โทเคน/ค่าใช้จ่ายเกินคาด

<!--
ค่าใช้จ่ายในการใช้ API key มี spend limit กำกับอยู่
สิ่งที่ต้องระวังคืองานที่วนซ้ำหรือรันเป็นเวลานาน เพราะจะใช้โทเคนสะสมมาก
และอาจชนวงเงินโดยไม่รู้ตัวถ้าไม่ได้เฝ้าดู
-->

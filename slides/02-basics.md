```
เราจะทำงานบน remote VM ผ่านคำสั่ง `ssh myvm "..."`
โปรเจกต์ตัวอย่างอยู่ที่ `~/cc-basics` บน VM แล้ว (provision ไว้ให้แล้ว)
ใช้ ssh คำสั่งนี้อ่าน/แก้ไฟล์และรันคำสั่งทุกครั้งตลอด lab นี้
```

<!-- ให้ทุกคนพิมพ์ prompt นี้เป๊ะ ๆ ก่อน อย่าข้ามขั้นนี้ไปเริ่มโจทย์ที่ 1 ตรง ๆ -->

## ขั้นที่ 3 — สิ่งที่จะเห็นต่อจากนี้ (ปกติ ไม่ต้องแปลกใจ)

- Claude จะเริ่มพิมพ์คำสั่งหน้าตาเหมือน `ssh myvm "cd ~/cc-basics && ..."` ทุกครั้งที่ต้อง
  อ่าน/แก้ไฟล์หรือรันคำสั่ง — นี่คือ Claude "เข้าไปทำงาน" บน VM แทนเราผ่าน SSH ที่ตั้งไว้แล้ว
- ก่อนรันคำสั่งแรกจะมี **permission prompt** ถาม — กด allow ได้เลย (ไม่ใช่ error)
- ถ้า Claude "ค้าง" นานผิดปกติหลังยิง ssh → สงสัยว่า ssh ไม่ non-interactive กลับไปดู
  Checkpoint SSH ใน lab 01

<!--

มาก่อนอาจตกใจ ต้องบอกว่าเป็นเรื่องปกติ และสอนวิธีสังเกตอาการค้างที่ผิดปกติ (เชื่อมกับ
Checkpoint 0 ของ lab 01) แยกจากการทำงานตามปกติ

สรุปเนื้อหาไฟล์จริงได้ก่อนไปต่อ ถ้ามีคนค้างให้ช่วยตรงนี้ก่อน ดีกว่าไปเจอปัญหาในโจทย์ที่ 1

## 1. คุยกับ Claude Code (prompting) (10 นาที)

ลอง:
```
อธิบายว่าโปรเจกต์นี้ทำอะไร โดยอ่านจากไฟล์ในโฟลเดอร์
```

เคล็ดลับ: บอก **เป้าหมาย + บริบท + ตัวอย่าง** ยิ่งชัด ผลยิ่งดี

<!--
นี่คือ prompt แรกของ lab — เน้นให้ผู้เรียนสังเกตว่า Claude อ่านไฟล์เองได้โดยไม่ต้องบอกชื่อไฟล์ทีละไฟล์.
ย้ำเคล็ดลับ "เป้าหมาย + บริบท + ตัวอย่าง" เป็นหลักการ prompting ที่จะใช้ตลอดทั้งวัน ให้ผู้เรียนจดไว้.
ให้เวลาผู้เรียนลองพิมพ์เองจริง ๆ ไม่ใช่แค่ดูสไลด์.
-->

## 2. แก้ไฟล์ (15 นาที)

```
เพิ่มฟังก์ชัน multiply(a, b) ใน src/calculator.js พร้อมคอมเมนต์ภาษาไทยสั้น ๆ
```

- ดู **diff** ที่ Claude เสนอ ก่อนกด allow
- ลองสั่งแก้ต่อ: `เปลี่ยนชื่อ multiply เป็น mul และอัปเดตที่เรียกใช้ทั้งหมด`
- ตรวจเองได้ผ่าน ssh เช่นกัน: `ssh myvm "cat ~/cc-basics/src/calculator.js"`

<!--
จุดสำคัญที่สุดของสไลด์นี้คือ "ดู diff ก่อนกด allow" — ห้ามข้ามขั้นนี้ ให้ผู้เรียนอ่าน diff จริงก่อนอนุมัติ.
สอนว่าการสั่งแก้ต่อเนื่อง (rename + อัปเดตที่เรียกใช้ทั้งหมด) แสดงว่า Claude เข้าใจ context ของงานก่อนหน้า ไม่ต้องอธิบายซ้ำทั้งหมด.
เดินดูหน้าจอผู้เรียนว่าเห็น diff และกด allow/deny ถูกจังหวะหรือไม่ ถ้าอยากยืนยันเองก็ ssh เข้า VM ไปดูไฟล์ได้ตรง ๆ.
-->

---

## 3. รันคำสั่ง & permission (10 นาที)

```
รันเทสต์ให้หน่อย
```

สังเกตว่า Claude ขออนุญาตก่อนรันคำสั่ง — เข้าใจว่า **เราคุมได้เสมอ** ว่าจะให้รันอะไร

<!--
ประเด็น safety ที่สำคัญมาก: ต้องย้ำว่า Claude จะขอ permission ก่อนรันคำสั่งเสมอ (ไม่ใช่รันลับหลัง).
ให้ผู้เรียนลองกด deny ดูสักครั้งเพื่อดูว่าเกิดอะไรขึ้น จะช่วยให้เข้าใจว่าเราคุมสถานการณ์ได้จริง.
ถ้ามีคนถามเรื่อง auto-approve/permission mode สามารถพูดคร่าว ๆ ได้ แต่รายละเอียดลึกเก็บไว้ช่วงอื่น.
-->

---

## 4. Slash commands (10 นาที)

พิมพ์ `/` เพื่อดูคำสั่งที่มี ลองใช้:
- `/help` — ความช่วยเหลือ
- `/clear` — ล้าง context เริ่มใหม่
- `/commands` หรือดูรายการ skill/commands ที่ติดตั้ง

<!--
ให้ผู้เรียนพิมพ์ "/" จริง ๆ ในเทอร์มินัลของตัวเอง เพื่อเห็น autocomplete ของ slash commands.
เน้นว่า /clear มีประโยชน์เมื่อ context รกหรือเปลี่ยนงาน — ไม่ต้องปิดโปรแกรมใหม่.
บอกว่า /commands หรือรายการ skills ที่ติดตั้งจะเชื่อมไปสู่ lab 03 (Skills) ในช่วงบ่าย ให้ผู้เรียนสังเกตไว้ก่อน.
-->

---

## 5. Git (10 นาที)

```
git init ให้หน่อย แล้ว commit งานปัจจุบันด้วยข้อความที่เหมาะสม
```

ดูว่า Claude รัน git ให้อย่างไร (ขออนุญาตก่อน)

<!--
ย้ำอีกครั้งเรื่อง permission — git init และ git commit ก็ต้องขออนุญาตเหมือนคำสั่งอื่น ไม่มีข้อยกเว้น.
ให้ผู้เรียนสังเกตข้อความ commit ที่ Claude ร่างให้ว่าเหมาะสม/สื่อความหมายหรือไม่ อาจให้ลองแก้ข้อความก่อน commit จริง.
ถ้าใครมี git repo อยู่แล้วในโฟลเดอร์ ให้เช็คก่อนว่าจะไม่ชนกับ repo เดิม.
-->

## 6. Plan mode — ปูทางช่วงบ่าย (10 นาที)

สำหรับงานใหญ่ ให้ Claude **วางแผนก่อนลงมือ**:

```
ฉันอยากเพิ่มฟีเจอร์อ่านไฟล์ CSV เข้ามาใน calculator นี้
ช่วยวางแผนก่อน (plan mode) อย่าเพิ่งแก้โค้ด
```

- Claude ร่างแผนให้ตรวจ → เราแก้/อนุมัติได้
- อนุมัติแล้วจึงลงมือ

<!--
plan mode เหมาะกับงานที่มีหลายขั้นตอนหรือกระทบหลายไฟล์ — สอนให้ผู้เรียนรู้จักใช้ก่อนงานใหญ่เสมอ.
เน้นว่าแผนที่ Claude ร่างมาแก้ไขได้ ไม่ต้องรับตามที่เสนอทั้งหมด — ให้ผู้เรียนลองต่อรอง/ปรับแผนก่อนอนุมัติจริง.
เตรียมผู้เรียนว่า concept นี้จะเชื่อมโยงกับงานสร้างจริงในช่วงบ่าย (lab 04).
-->

## `CLAUDE.md` — จำกติกาของโปรเจกต์

สร้างไฟล์นี้ในโปรเจกต์เพื่อบันทึกกติกา/บริบทที่อยากให้ Claude จำทุกครั้ง

```
สร้าง CLAUDE.md อธิบายว่าโปรเจกต์นี้ใช้ Node, เขียนคอมเมนต์เป็นภาษาไทย, และใช้ conventional commits
```

<!--
CLAUDE.md คือไฟล์ context ที่ Claude จะอ่านทุกครั้งที่เริ่มงานในโปรเจกต์นี้ — เหมือน "คู่มือทีม" ที่ไม่ต้องอธิบายซ้ำ.
ยกตัวอย่างกติกาที่ใส่ได้: ภาษาที่ใช้เขียนคอมเมนต์, รูปแบบ commit message, framework ที่ใช้, ข้อห้าม/ข้อควรระวัง.
ย้ำว่าไฟล์นี้ยิ่งเขียนดี ยิ่งลดการอธิบายซ้ำในทุก session ต่อไป — คุ้มที่จะลงทุนเวลาทำให้ครบ.
-->
